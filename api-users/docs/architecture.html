Flujo de refresh (el más delicado)

  1. Se calcula el hash SHA-256 del token recibido y se busca.
  2. No existe → 401. Ya revocado → se revoca toda la familia (robo) y 401. Expirado → 401.
  3. Cuenta bloqueada o borrada → 401.
  4. TryRotateAsync atómico (UPDATE condicional): si pierde la carrera → revoca familia y 401.
  5. Éxito → nuevo access token (15 min) + nuevo refresh (7 días) en la misma familia.

Modelo de datos

RefreshTokens: Id (PK), UserId (FK a AppUser, cascade), FamilyId, TokenHash (único, 64), CreatedAtUtc, ExpiresAtUtc, RevokedAtUtc?, ReplacedByTokenHash?. Índices: TokenHash (único), FamilyId, UserId. Más las tablas de Identity (AspNetUsers, AspNetRoles…).

Arranque y configuración

  • Orden: servicios → migrar y sembrar (solo si Database:MigrateOnStartup=true) → ForwardedHeaders (opcional) → HSTS y redirección HTTPS (fuera de Development) → OpenAPI/Scalar (solo Development) → límite de peticiones → auth → endpoints.
  • Database:Provider: SqlServer | PostgreSql. ConnectionStrings:Default, Jwt:SigningKey (≥32 bytes) y Admin:* van como secretos.
  • RateLimiting:AuthPermitLimit y AuthWindowSeconds (20 por 60 s por IP, ventana deslizante). ForwardedHeaders:* viene desactivado; al activarlo hay que listar los proxies o la API no arranca.
  • Docker: SQL Server por defecto, PostgreSQL con el perfil postgres.

Añadir una feature

  1. Domain: solo si hay regla propia.
  2. Application: caso de uso, DTOs y puerto para todo acceso externo.
  3. Infrastructure: implementar el puerto y registrarlo en AddInfrastructure.
  4. Cambio de esquema: migración en ambos proyectos de migraciones.
  5. Api: endpoint con validación, Produces* y registro en Program.cs.
  6. Tests de integración en ambos motores; ArchitectureTests debe seguir en verde.

Trampas conocidas

  • Claims sub y role sin mapear (MapInboundClaims=false).
  • Los records de request son nullables a propósito para devolver 400 en cuerpos incompletos.
  • Sin MigrateOnStartup tampoco se siembra admin ni roles.
  • No actives ForwardedHeaders sin indicar los proxies: con listas vacías el framework confiaría en cualquier cliente.
  • Los tests fijan un límite de peticiones muy alto (ApiFactory), porque la suite hace muchas llamadas a /auth desde una sola dirección.

Limitaciones conocidas

  • Sin confirmación de email: se puede registrar el email de otra persona.
  • El 409 del registro revela que un email existe.
  • Los refresh tokens vencidos o revocados no se purgan.
  • Una sola clave de firma HS256, sin kid ni ventana de rotación.
  • El límite de peticiones es en memoria y por instancia.
