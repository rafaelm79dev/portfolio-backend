api-services-kafka

Dos servicios .NET, cada uno con su base de datos, que se comunican solo por Kafka.

Componentes

orders-apiCrea los pedidos y le pide el stock a inventory. Después marca cada pedido como confirmado o rechazado.Puerto 8081
Base de datos de pedidosPostgreSQLPuerto 5433
inventory-apiReserva el stock de un pedido, todas las líneas o ninguna, y responde.Puerto 8082
Base de datos de inventarioPostgreSQLPuerto 5434
KafkaEl único vínculo entre los dos servicios. Dos topics, orders.events e inventory.events, y un topic de mensajes fallidos (dead-letter) para cada uno.Puerto 9092 · Kafka UI en el puerto 8085

Un servicio nunca lee la base de datos del otro ni lo llama por HTTP. Solo comparten los tipos de mensaje.

Cómo fluye un pedido

  1. El cliente crea un pedido. orders-api lo guarda como Pending, junto con el evento que debe enviar, y responde enseguida.
  2. orders-api publica OrderCreated en Kafka.
  3. inventory-api lo lee y reserva el stock. Responde con StockReserved o StockRejected.
  4. orders-api lee la respuesta y deja el pedido en Confirmed o Rejected.
  5. El cliente consulta el pedido y ve el estado final.

Hasta que llega la respuesta, el pedido está en Pending. Los dos servicios se ponen de acuerdo tras un instante (consistencia eventual).

Cuando algo falla

SituaciónQué pasa
Kafka no está disponibleLos pedidos se aceptan igual. Los eventos esperan en la base de datos y salen cuando Kafka vuelve.
Un mensaje llega dos vecesEl consumidor lo reconoce y no hace nada. El stock no se descuenta dos veces.
Falla el procesamiento3 intentos. Si todos fallan, el mensaje va al topic de mensajes fallidos con la causa.
Dos pedidos por la última unidadUno se queda con la unidad y el otro se rechaza. El stock nunca queda negativo.

Puesta en marcha

docker compose up --build levanta todo. En el README están los comandos para probarlo y qué mirar en Kafka UI.

Limitaciones conocidas

  • Si una respuesta acaba en el topic de mensajes fallidos, el pedido se queda en Pending. Nada lo reprocesa.
  • No hay flujo de cancelación, así que el stock reservado nunca se libera.
  • Sin autenticación, y Kafka y las bases de datos no tienen usuario ni cifrado: úsalo en una red cerrada.
